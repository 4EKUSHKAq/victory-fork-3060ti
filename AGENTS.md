# Правила работы с репозиторием и внешними форками

1. **Изучение документации и аудит:** Перед любыми правками всегда читай `README.md` и папку `docs/`. Сначала проведи аудит задачи и объясни пользователю простым русским языком, как сейчас устроен этот участок кода и нужен ли вообще фикс, прежде чем писать код.
2. **Безопасность веток:** Никогда не правь ветку `main` напрямую. Перед любой задачей создавай новую ветку (`git checkout -b <название_задачи>`).
3. **Умный поиск (`gh`):** Для поиска готовых решений в апстриме (`Marvisak/VIctory`) и соседних форках используй утилиту `gh` (`gh pr list`, `gh pr view`, `gh issue list`). Переноси только конкретные проверенные изменения в отдельную ветку.
4. **Экономия контекста («Эстафета»):** Веди в корне файл `HANDOFF.md` с текущим статусом, списком шагов и результатами замеров. Выполняй строго один шаг из плана за раз, обновляй `HANDOFF.md` и останавливайся для отчёта пользователю. С Раунда 11 старые разделы (§1–§28, раунды 1–6) вынесены в `HANDOFF-archive.md` — в основном файле только актуальные §29+, чтобы не тратить контекст; новые раунды добавлять туда же, а историю не раздувать.
5. **Защита от перерасхода токенов:** Никогда не пытайся читать бинарные файлы (`.exe`, `.dll`, `.rpf`) как текст — используй для этого инструменты реверс-инжиниринга и встроенные флаги отладки проекта.
6. **Обязательная проверка:** После любого изменения кода запускай `cargo check --workspace` и `cargo test --workspace`. Если сборка падает — чини сразу.
7. **Тщательность и A/B-контроль:** Вносить только по одному логическому изменению за шаг; перед переносом чужого кода построчно сверять индексы дескрипторов, root-таблиц и лимиты 8 ГБ VRAM; если замер после правки показывает падение FPS или новые визуальные артефакты — немедленно откатывать правку и разбирать причину.
8. **Мониторинг и перенос наработок:** В начале каждого раунда проверять все **7** репозиториев звёздного списка — `fxceless/victory-fork`, `Marvisak/VIctory`, `stellarr-studio/kelvaroq`, `Belobug/VIctory-Belobug-AMD`, `uiliannn/VItoriaBr`, **`xcl-dev/xcl`** и **`zortos293/XSEmu`** — на новые полезные фиксы CPU/VRAM/рендера (через `gh`, не `git fetch`) и включать их в план раунда. Лицензии: `xcl` — GPL-2.0, **только идеи/факты/цифры, код не переносить**; `XSEmu` — третья линия мониторинга (GPL-2.0-only заявлена, но 6 файлов GPL-3.0-or-later с provenance — перенос только из них и с provenance-нотой). Для каждого кандидата фиксировать номер PR/коммита, затронутые файлы, риск и ожидаемый эффект; переносить только проверенные изменения с A/B-замером.
   **NVIDIA-линия (с раунда 10; приоритет 80/20 закреплён в Раунде 20):** дополнительно проверять NVIDIA-ориентированные деревья — `trustno1-coder/VIctory-NVIDIA`, `readmet3xt-lab/foxhound`, `Steenax6/VIctory-NVID`, `Xeltax/VIcky`, `101Leafy/victory-leafy`, `Fayberr/Victory-United` — на фиксы конкретно под NVIDIA (водные плиты, view-heap лимит 1 000 000, wave64/32-lane, AV в heap_direct_texture_reads, native 1440p, DLSS/Streamline). Чужой скомпилированный **exe не запускать** — только исходники/доки/диффы; перенос кода — с provenance-нотой (репозиторий + коммит + файл) и A/B-замером.
   **`trustno1-coder/VIctory-NVIDIA` — главный источник (80 % внимания разведки).** В начале КАЖДОГО раунда, до любых правок, обязательно:
   `git -C C:\GTA6_Port\victory-nvidia-test fetch origin`, затем `git -C C:\GTA6_Port\victory-nvidia-test log --oneline --stat <прежний-HEAD>..origin/main` — разобрать **каждый** новый коммит (файлы, +/−, суть, применимость к нашему профилю 3060 Ti 8 ГБ / wave32 / 1080p-рендер) и каждый новый PR (`gh pr list -R trustno1-coder/VIctory-NVIDIA --state all --limit 100`), включая продолжения серии водных патчей (`5dc3b259…`, `6f225b64…`), `land.rs`/`safecopy.rs`, `watch`/refresh/copy-back, память 8 ГБ и Streamline. Новый HEAD их `origin/main` фиксировать в HANDOFF раунда.
   **Остальные отслеживаемые репозитории — 20 % внимания:** в начале раунда только поверхностный скан заголовков свежих PR/issues за последние ~24 ч (`gh pr list --state open --limit 30` по каждому: `Marvisak/VIctory`, `fxceless/victory-fork`, `stellarr-studio/kelvaroq`, `Belobug/VIctory-Belobug-AMD`, `uiliannn/VItoriaBr`, `xcl-dev/xcl`, `zortos293/XSEmu`, `readmet3xt-lab/foxhound`, `Steenax6/VIctory-NVID`, `Xeltax/VIcky`, `101Leafy/victory-leafy`, `Fayberr/Victory-United`), глубокие аудиты — только если заголовок прямо про наш профиль. **Если один и тот же фикс есть в нескольких репозиториях, приоритет версии из `VIctory-NVIDIA`** (она адаптирована под wave32/NVIDIA), и только при её отсутствии берётся версия из другого репо. Обязательный скан свежих PR апстрима `Marvisak/VIctory` в каждом раунде остаётся: `gh pr list -R Marvisak/VIctory --state open --limit 100`, отбирать только чинящее наш профиль.
9. **Тихий фоновый харнесс (с раунда 11):** тестовые авто-прогоны идут фоном и не мешают работе пользователя. В `run-road.ps1` **запрещены** `HWND_TOPMOST`/`SetWindowPos(HWND_TOPMOST)`, `sendkeys2.ps1`, `AttachThreadInput`, `SetForegroundWindow`, `keybd_event`/Alt+F4 и любые физические нажатия: окно игры — обычное компактное `1280×720` в нормальном z-порядке (HWND_NOTOPMOST, SWP_NOACTIVATE), EULA уже принят в профиле, метрики берутся из `err.log`, `nvidia-smi` и капшена (`captions.log`), скриншоты — `CopyFromScreen` по rect окна. `launch-game.ps1` для интерактивной игры тоже не делает окно topmost (фокус — один раз при запуске).
10. **DLSS/Streamline (с раунда 11):** официальные DLL NVIDIA (`sl.interposer.dll`, `sl.common.dll`, `sl.dlss.dll`, `nvngx_dlss.dll` и др., Streamline SDK v2.14.16) в репозиторий не коммитить и не распространять — они лежат вне дерева (по умолчанию `C:\GTA6_Port\streamline\bin\x64`, путь — `VICTORY_STREAMLINE_DIR`, лицензии рядом с DLL). Реализуется только Super Resolution (`VICTORY_DLSS`), Frame Generation на RTX 30 — NO-GO. Вся интеграция идёт через перехват `ffx*` IAT и `slEvaluateFeature` в host-command-list; `victory-shader` не трогать, кэш `shaders-r8-group2` должен остаться целым, а при любой проблеме Streamline игра обязана молча откатиться на родной апскейлер заголовка (`VICTORY_DLSS=0` — гарантированный откат).
